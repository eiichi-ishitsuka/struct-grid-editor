# AI開発ワークフロールール (AI Development Workflow Rules)

本リポジトリにおいて、AIエージェントおよび開発者が機能開発・改修・リファクタリングを行う際は、以下の6つのステップを標準開発プロセスとして厳守してください。

---

## 開発プロセス全体フロー

```
[1. 実装計画の策定]
       ↓
[2. アーキテクチャ変更時の ADR 作成] (該当時のみ)
       ↓
[3. 実装の推進 (内側から外側へ)]
       ↓
[4. テストの作成 (JSDoc 観点付与)]
       ↓
[5. テスト・静的解析のパス確認]
       ↓
[6. ドキュメントの一括自動生成]
```

---

## 1. まずは実装計画を立てる (Planning)
- **目的**: 変更の影響範囲と設計妥当性を事前に担保し、手戻りを防止する。
- **実施事項**:
  - 要件と課題の背景を整理する。
  - 影響を受けるレイヤー（Domain / Application / Infrastructure）と変更対象ファイルを特定する。
  - 実装手順（依存の少ない内側レイヤーから順序付け）と検証計画を策定する。
  - 大きな機能追加や破壊的変更を伴う場合は、ユーザーに計画を提示して合意を得る。

---

## 2. 根本的なアーキテクチャ変更がある場合は ADR を作成する (ADR Creation)
- **目的**: 設計の背景・選定理由・トレードオフを記録し、将来の保守性と一貫性を担保する。
- **対象ケース**:
  - レイヤー間の責務・依存関係の変更
  - コアな外部ライブラリ（パーサー、テストツール、ドキュメントツール等）の導入・差し替え
  - ドメインモデルやデータ構造変換の根本的アプローチの変更
- **実施事項**:
  - `docs/adr/` 配下に連番（例: `007-xxx.md`）で ADR ファイルを新規作成する。
  - ステータス、コンテキスト（背景・課題）、決定（採用アーキテクチャ・選定結果）、結果（メリット・デメリット）を明記する。

---

## 3. 実装を進める (Implementation)
- **目的**: クリーンアーキテクチャとコーディング規約を遵守した高品質なコードベースを維持する。
- **実施事項**:
  - **依存方向の遵守**: 常に「Domain（ドメインモデル） → Application（ユースケース） → Infrastructure（VS Code / Webview / パーサー）」の内側から外側へ向けて実装する。
  - **ドメイン層の保護**: 外部ライブラリ（`vscode`, `fs`, `yaml` 等）をドメイン層に直接依存させない（`src/domain/port/` のインターフェース経由で DIP を適用）。
  - **不変性の維持**: Value Object はイミュータブルとし、変更時は新しいインスタンスを返す。
  - **日本語 JSDoc / コメントの徹底**: TypeDoc でドキュメント出力されるクラス・インターフェース・メソッド・引数・戻り値の説明、およびコード内コメントはすべて日本語で記述する。
  - **規約の厳守**: `any` 型を避け、絵文字は一切使用しない。


---

## 4. テストを作成する (Test Authoring)
- **目的**: 機能の正確性を検証するとともに、生きた仕様書（Living Documentation）としての基盤を構築する。
- **実施事項**:
  - 新規機能や変更ロジックに対応する単体テストを `src/test/` 配下に必ず追加する。
  - **JSDoc コメントの必須付与**:
    各テスト関数（`it(...)` または `test(...)`）の直前に、必ず日本語で以下のフォーマットの JSDoc を付与すること:
    ```typescript
    /**
     * 【観点】テストの着眼点・目的（例: レコード間で欠損キーがある場合の処理確認）
     * 【テスト内容】具体的な入力値・操作手順と期待される検証結果
     */
    it('...', () => { ... });
    ```
    ※このコメントは後続ステップで「テスト仕様書」として自動抽出・文書化されます。

---

## 5. テストがパスすることを確認する (Verification)
- **目的**: リグレッションをゼロにし、既存機能および新規機能の完全動作を保証する。
- **実施事項**:
  - 単体テストの実行: `npm run test:unit` が全件パスすることを確認する。
  - 型チェックの実行: `npm run check-types` で TypeScript のコンパイルエラーがゼロ件であることを確認する。
  - Linter の実行: `npm run lint` で ESLint の警告・エラーがゼロ件であることを確認する。
  - （必要に応じて）拡張機能のバンドル検証: `npm run compile` または `node esbuild.js` を実行する。

---

## 6. ドキュメントを生成する (Documentation Generation)
- **目的**: ソースコードおよびテスト仕様とドキュメントの乖離をなくし、常に最新の仕様書を維持する。
- **実施事項**:
  - ドキュメント生成コマンドの実行:
    ```bash
    npm run doc
    ```
  - **生成・更新される成果物**:
    1. **ソースコード API 仕様書**: [`docs/api/`](../api/) 配下の Markdown 群（TypeDoc）
    2. **テスト仕様書**: [`docs/test-specifications.md`](../test-specifications.md)（各テストの【観点】【テスト内容】一覧）
  - **Markdown 統一原則**: すべてのドキュメント出力は Markdown（.md）形式とし、HTML などの非 Markdown アセットを出力・コミットしないこと。
  - **Git管理の徹底**: 生成された `docs/api/` および `docs/test-specifications.md` はコード本体と同期させて Git 管理（コミット対象）に含めること。
